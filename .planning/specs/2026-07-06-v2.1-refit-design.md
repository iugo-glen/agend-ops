# agend-ops v2.1 Refit — "Operate, Don't Build"

**Date:** 2026-07-06
**Status:** Approved design (brainstormed with Glen; four-part failure diagnosis confirmed)
**Supersedes:** v2.0 "Autonomous Operations" milestone direction (78% complete, paused)

## 1. Context and Diagnosis

agend-ops v1/v2.0 shipped 12 GSD phases (triage, task executor, invoicing, briefings, action queue, Next.js dashboard on Coolify, Obsidian vault layer, calendar/drive enrichment) between March and June 2026 — and was used in anger for approximately one day (2026-03-23: the only briefing ever generated). Glen confirmed all four failure causes:

1. **The unattended loop never ran.** GitHub Actions cron was disabled 2026-05-21 after 30+ failures; the required secrets were never provisioned. The system only worked when Glen manually opened a session — so it never became a habit.
2. **Output landed in the wrong place.** Briefings went to a repo and a dashboard Glen had to visit. His attention lives in starred Gmail, Apple Reminders, Apple Notes, and his phone.
3. **Triage quality wasn't trustworthy enough** to rely on when it did run.
4. **Building outcompeted operating.** Twelve phases of construction, one briefing of use; competing priorities (dashboard work, client work, workflows builds) filled the vacuum.

The refit addresses all four with minimal new construction. The existing architecture (git as source of truth, NDJSON + schemas, hardened no-send Gmail MCP, action queue) is retained unchanged.

## 2. Goals

- The loop runs unattended every business day with zero manual invocation.
- All output is pushed into surfaces Glen already inhabits: Gmail Drafts, Apple Reminders, Apple Notes, and a Multica kanban board.
- Triage becomes trustworthy via an authored context pack plus a graded feedback loop.
- Glen's six-role workload is reduced role-by-role via incremental "role packs", starting with invoicing.
- Total build effort capped at 2–3 days, followed by a hard operate-only month.

## 3. Non-Goals

- No new Obsidian phases, dashboard features, or additional surfaces during the operate-only month.
- No autonomous external sends. Trust boundary is **draft everything, Glen approves sends** (his explicit choice, 2026-07-06). The hardened no-send MCP enforces this structurally.
- Not replacing agend-ops with Multica. Multica is a disposable projection, never the source of truth.
- Not hiring decisions — this system generates the evidence for a future hire decision; it does not make one.

## 4. Architecture

### 4.1 Canonical core (unchanged): agend-ops repo

`data/` NDJSON remains the single source of truth for triage results, tasks, todos, invoices, briefings, action queue, and the activity feed. All schemas in `schemas/` remain authoritative. The Next.js dashboard and static Pages view remain as audit/glance surfaces but are no longer the primary interface.

### 4.2 The loop: local launchd, not cloud

- A launchd job runs `claude -p` in the agend-ops repo on a business-day schedule. (Note: the existing `mac/` plist is a `KeepAlive` watcher daemon, not a `StartCalendarInterval` schedule — the scheduled/run-on-wake behavior is new ground, hence the verification gate below.)
  - **~07:30 ACST** — full triage (inbox + starred sweep) + daily briefing + surface push
  - **~12:30 ACST** — incremental sweep + surface push
  - **~16:30 ACST** — end-of-day sweep + tomorrow-prep notes
- Local execution uses the Mac's already-authenticated MCP servers (hardened-workspace, Xero, etc.). **No secrets provisioning** — this removes the exact blocker that killed v1's automation.
- **Headless preconditions (day 1, before the schedule goes live):** two things silently break a launchd-spawned `claude -p` and must be pre-cleared, or this becomes v2.1's "secrets were never provisioned":
  1. **Tool permissions.** Non-interactive runs cannot answer permission prompts — an MCP/tool call that would prompt just fails. Every tool the loop uses must be pre-authorized (allowlist in `.claude/settings`, or a dedicated permission mode for the loop's run prompt).
  2. **macOS TCC/automation consent.** The first osascript control of Reminders and Notes triggers a consent dialog; from launchd it may fail silently instead of prompting. Run each osascript path once interactively to grant consent before scheduling.
- **Loop verify-first gate (day 1):** the loop is not "built" until a *launchd-triggered* (not terminal-triggered) run has completed triage → Reminder → Note end-to-end with zero human touch.
- **Idempotency:** three runs/day means the 12:30 run must not re-draft the 07:30 run's output or duplicate Reminders/cards. Each run appends to a run ledger (`data/runs/` NDJSON) and every pushed artifact carries a dedupe key (message/thread id + date); runs check the ledger before creating anything.
- GitHub Actions cron stays retired. The workflow file may be deleted or left disabled.
- **Failure visibility — dead-man's switch, not error alerts:** an error-triggered alert cannot catch the worst failure (Mac off / job never fired — nothing executes, so nothing alerts; launchd runs missed calendar jobs on *wake* but not after a *boot*). Instead, a recurring daily Apple Reminder ("⚠️ ops loop didn't run today", due ~18:00) exists in advance; the loop's last successful step each day completes/deletes it. Silence surfaces by default. The wrapper additionally writes an immediate "⚠️ ops loop failed — <date> <run>" Reminder on error, but the dead-man's switch is the primary safety net.

### 4.3 Push surfaces

| Surface | Content | Mechanism |
|---|---|---|
| **Gmail Drafts** | Every prepared outbound email (chasers, replies, consultant coordination). Drafts folder IS the approval queue; approval = Glen presses Send. | hardened-workspace MCP (create-draft only; cannot send) |
| **Apple Reminders** ("Agend — Decisions" list) | The 3–5 decisions only Glen can make, with context in the note body and sensible due dates. Also loop-failure alerts. | osascript (local loop makes this possible) |
| **Apple Notes** ("Agend Ops" folder) | One briefing note per day. | osascript |
| **Multica board** | Actionable triaged items as cards (see 4.4). | Multica API |
| **Starred Gmail** (input, not output) | Star = "needs Glen/follow-up". The sweep ingests starred messages, creates tracked follow-ups, and reminds when threads go quiet. Glen's existing habit is preserved, its "I have to remember" hole is closed. | hardened-workspace MCP |

### 4.4 Multica: board + dispatch surface

- Self-hosted (Docker Compose; candidate host is the existing Coolify box). Satisfies the data-ownership constraint.
- **agend-ops → Multica (one-way canonical):** the loop creates/updates cards for actionable triaged items.
- **Multica → agend-ops:** card status changes and Glen's drag/assign actions flow back as `data/queue/actions.jsonl` entries — the identical pattern the dashboard action queue already uses. The loop processes them next run.
- **Dispatch (DEFERRED — not in the build cap):** the eventual goal is card→agent dispatch to a Claude Code runtime on the Mac, superseding the v1 `task-executor` path for board-visible work. It is explicitly **out of scope for the 2–3 day build**: it is v1's construction gravity in miniature, and it turns card creation into remote code execution on the Mac — it does not ship without an authenticated dispatch channel design. It gets built only if the friction log earns it after the operate-only month.
- **Exposure:** Multica on the Coolify box holds client names and task summaries. It must sit behind auth (at minimum Multica's own login; preferably not publicly routed at all — LAN/tailnet or reverse-proxy allowlist). This is a day-1 checklist item, not an afterthought.
- **Disposability rule:** if Multica is removed, only a view is lost. No data lives solely in Multica.
- **Verify-first gate (build day 1):** stand up Multica, programmatically create a card and read a status change **before** wiring any sync. Fallback if the API check fails: a board-column view in the existing Next.js dashboard over the same data. If the gate eats more than a half-day, take the fallback and move on — the board is the most deferrable piece of the refit; the habit-former is launchd + Drafts + Reminders + Notes.

### 4.5 Triage quality: authored brain + graded feedback

- **Context pack** in `data/config/`: client roster with tiers, VIP senders, routine-vs-judgement rules, current company priorities. (`data/config/clients.jsonl` already exists and seeds the roster.) Authored with Glen in one sitting; maintained by the loop thereafter. Every run reads it. (Rationale: Glen's own guardian-architecture benchmark finding — agentic + authored memory outperforms generic context.)
- **Implicit feedback:** drafts sent unedited vs edited vs deleted; Reminders completed vs ignored; cards moved vs stalled. A **weekly self-review run** (a fourth launchd schedule, built day 3 as a simple run prompt) reads these signals and proposes context-pack rule adjustments (proposals into the briefing, never silent edits). Draft outcomes are measured by comparing the loop's draft ledger against the Sent folder via the read-only MCP — this comparison is the only non-trivial machinery here; if it isn't reliable by end of day 3, the weekly review falls back to grade data only and the draft-outcome signal is dropped from month-1 measurement.
- **Graded shadow mode (weeks 1–2):** each briefing ends with a 👍/👎 prompt; grades are logged and tuned against before Glen is asked to *rely* on triage.
- **Schemas:** per repo convention, new NDJSON record types ship with schemas — `schemas/` gets definitions for the run ledger, `friction.jsonl`, and context-pack records as part of the build days.

**Hire question:** run the refit 6–8 weeks; the friction log (things agents provably couldn't do) becomes the job description for any future ops/EA hire.

## 6. Guardrails

- **Build cap:** 2–3 days total, then a hard operate-only month. The only permitted "building" during that month is context-pack rule edits and bug fixes that block the loop.
- **KPI:** consecutive business days the loop ran AND produced something Glen used. Not features shipped.
- **Friction log:** the loop maintains `data/friction.jsonl` — anything it couldn't do, was wrong about, or Glen overrode. This is the sole input for deciding what (if anything) gets built after the month.

## 7. Build Outline (fits the 2–3 day cap)

1. **Day 1:** launchd wrapper + `claude -p` run prompt; tool-permission allowlist + osascript TCC consent granted interactively; osascript Reminders/Notes push; dead-man's-switch Reminder wired; **loop gate passed** (a launchd-triggered run completes triage → Reminder → Note untouched). Multica stood up behind auth + API verified (gate; half-day time-box, fallback = dashboard board view).
2. **Day 2:** starred-sweep + triage prompt refit against context pack (authored with Glen same day); Gmail-draft approval flow confirmed end-to-end; run-ledger idempotency (no duplicate drafts/Reminders across the three daily runs); Multica sync (cards out, actions.jsonl back).
3. **Day 3:** invoicing pack (Xero watch → chaser drafts); graded shadow-mode plumbing; weekly self-review run (draft-vs-Sent comparison, grade rollup, rule proposals); new-record schemas; dry-run of all three daily runs from launchd.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Mac asleep/off at run time | launchd fires on wake for missed intervals (asleep case); missed jobs do NOT replay after a boot (off case) — the dead-man's-switch Reminder covers both by firing unless the loop completed. Loop is idempotent per day via the run ledger. |
| Headless run silently blocked (permission prompt, TCC consent, expired auth) | Day-1 preconditions checklist (allowlist + interactive TCC grant); loop gate requires a launchd-triggered end-to-end pass before the schedule is trusted; dead-man's switch catches later regressions. |
| Multica immaturity / API gaps | Verify-first gate day 1, half-day time-box; disposability rule; dashboard-board fallback. |
| Multica exposure (business data on public box; dispatch = remote code execution) | Board behind auth / not publicly routed; dispatch deferred out of the build cap entirely, pending an authenticated channel design. |
| Triage trust never recovers | Graded shadow mode makes this measurable in 2 weeks instead of ambient disappointment; context pack is the tuning lever. |
| Construction gravity returns | Build cap + friction-log-only pipeline for new work; no new surfaces during operate month. |
| Prompt injection via email content | Unchanged v1 posture: hardened no-send MCP; drafts only; no file sharing; Glen is the send gate. osascript writes are local-only. |
| Token/subscription cost of 3 daily runs + weekly review | Watch usage in week 1; incremental sweeps (12:30/16:30) are scoped small; if cost surprises, drop to 2 runs/day before touching scope. |

## 9. Success Criteria (end of operate-only month)

- Loop ran unattended ≥ 90% of business days.
- Glen's starred-email count and "things I'm remembering in my head" measurably down (self-reported weekly).
- ≥ 70% of prepared drafts sent with no or minor edits (trust signal; measured by the weekly review's draft-vs-Sent comparison — if that machinery was dropped on day 3, substitute "≥ 70% of briefings graded 👍").
- Invoice chasers going out on time without Glen initiating them.
- A friction log substantial enough to either write a hire's job description or justify pack #2/#3 build time.
